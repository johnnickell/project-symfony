# Align Symfony Engineering Standards and Delivery

## Destination

Make the engineering conventions below the default for Symfony-owned planning, architecture, PHP, HTTP, tests,
quality checks, and delivery. Departures require a narrow, documented local justification rather than selective adoption
by preference. Bring existing owned code and contributor guidance into alignment through independently verifiable
slices while preserving the starter's current observable behavior and stronger verification requirements.

This is a Symfony-owned engineering epic, not the implementation handoff for the complete AccessControl starter.
Its destination is an aligned, verified foundation; it does not introduce authentication, persistence, application
APIs, or a release. The target is deliberately unversioned. `in-progress` records active planning, not completed
implementation or authorization to begin code changes without separately approved executable work under the
applicable local lifecycle.

## Decisions so far

John approved the stronger alignment direction in the planning conversation and requested this epic. The approval
covers the outcomes and exceptions recorded here; it does not approve dependency upgrades, runtime expansion,
publication, or removal of verification merely to resemble another application. These requirements are
self-contained local authority, not automatic incorporation of an external project's future policy changes.

silently reinterpreting existing records or treating the migration as already implemented.

### Ownership and architecture

- Preserve `App\` mapped directly to `src/` and dependencies pointing `Adapter -> Application -> Domain`.
  Symfony owns its composition root, namespace loading, autoconfiguration, aliases, compiler passes, and adapters;
  there is no Fight bundle. Preserve the boundary in [the local architecture rules](../agents/domain.md).
- Use public Fight package commands, queries, handlers, events, safe Views, and capability contracts directly when
  they express the use case. Do not copy package behavior or introduce aliases and forwarding wrappers merely to
  hide package names. Public-package changes remain with their owners.
- Introduce owned Application orchestration only when package behavior is insufficient and the use case enforces
  Symfony-owned application policy or coordinates real ownership boundaries. It must have observable inputs,
  outcomes/failures, behavior tests, and injected inward capabilities rather than service location.
- Keep business decisions with their Domain owner, coordination in Application, and transport/framework concerns
  in Adapter. A composition-root exception does not authorize service location in business code. CQRS alone
  establishes no transaction, delivery, retry, ordering, or idempotency guarantee.

### PHP, naming, and HTTP

- Standardize strict types, constructor injection, guard clauses, final classes and readonly properties where
  appropriate, and readonly value objects. Preserve justified framework/entity exceptions.
- Name capabilities for their behavior without an `Interface` suffix; name messages for intent or fact and
  handlers with `Handler`. Organize namespaces by demonstrated responsibility, not speculative Service, Manager,
  Helper, or other miscellaneous buckets. Never rename upstream APIs to enforce consumer taste.
- Use multiline docblocks with capitalized active-verb summaries and no terminal period, `Constructs ClassName`
  constructor summaries, and multiline `@inheritDoc` for inherited behavior. Retain the installed Fight Common
  PHPCS standard and reconcile local enforcement without modifying vendor code.
- Adopt one final invokable Action per HTTP interaction and explicit Responder ownership of status, headers, and
  representation. Actions translate transport context and delegate a package or justified owned use case; neither
  Actions nor Responders own business policy, persistence, transaction control, or authorization decisions.
- Align the existing homepage's presentation structure while preserving its route and rendered behavior. A purely
  presentational interaction needs no invented command, query, or Domain layer. Preserve explicit front-controller
  JSON middleware composition and bare-Kernel console behavior.
- For future APIs, cross presentation boundaries with safe Views rather than entities or secret-bearing values;
  keep PHP properties camelCase and explicitly map wire fields to snake_case. Authentication and transport gates
  must not replace authoritative authorization on non-HTTP entry paths. Exact API envelopes, errors, schemas, and
  endpoint semantics remain with [WF-003](../wayfinder/tickets/WF-003-adr-http-openapi-contract.md) and its dependent
  decisions; do not impose JSON/JSend on the HTML homepage.

### Tests and the canonical gate

- Tests prove meaningful owned behavior and important package integration contracts at the narrowest useful
  boundary, including success, rejection, failure, and effects where applicable. Record justified non-applicability.
  For bug repairs, obtain a failing regression test first where technically possible.
- Do not add product tests of wrappers, CI, configuration, planning/static-analysis tools, or test infrastructure,
  and do not manufacture invalid fixtures to test those tools. Review existing wiring-only tests individually:
  replace them with direct framework diagnostics only when equivalent evidence is identified and verified.
  Preserve meaningful owned-adapter unit tests and real integration/HTTP journeys, not just mock call sequences.
- Preserve exact 100% Unit-only owned-production statement coverage from
  [T-00007](../tickets/00007-TICKET.md). Keep direct coverage metadata and the separation of journey coverage;
  combined-suite coverage cannot satisfy the Unit requirement. Document the denominator, existing exclusions,
  driver, warnings, and gaps. Do not expand exclusions or dilute assertions to achieve alignment.
- Retain a distinct Unit coverage artifact through the end of the gate so later suites cannot overwrite the
  evidence used for acceptance. A coherent all-suite invocation is acceptable only if it independently proves
  the Unit-only requirement; otherwise preserve separate, non-duplicated suite runs.
- Make `./bin/build` a thin entrypoint for named, fail-fast PHP phase orchestration inside an already-running
  repository-owned Compose PHP service. Missing preparation must fail clearly. Do not rebuild an ephemeral image
  or install/update dependencies during every pre-submit invocation; dependency preparation is explicit.
- Preserve planning and Composer validation, PHP syntax, installed-standard PHPCS, PHPStan, Deptrac, Rector dry-run,
  exact Unit coverage, and every retained suite, each suite executed once. Existing planning validation may remain
  Python-owned; do not add Python quality-gate orchestration or duplicate planning logic in PHP.
- Update documented clean-clone preparation and hosted setup together. Hosted CI still delegates verification to
  the same `./bin/build`, not a parallel quality pipeline. Preserve noninteractive operation, failure propagation,
  worktree isolation, and separate local versus hosted evidence. Do not add frontend/browser suites before a
  locally authorized feature supplies those boundaries.

### Review and delivery

- Require independent Spec and Standards review of the exact implementation snapshot. One independent reviewer
  may perform both passes; the implementer's own checks are not independent acceptance.
- Tie acceptance and findings to the branch/base/head and relevant working-tree state, with requirements covered,
  commands/results, warnings, limitations, and remaining risks. A green build is not semantic review.
- Keep implementation completion, local verification, hosted status, independent acceptance, publication, merge,
  release, and deployment distinct. Preserve human merge control and existing explicit archive authority.
- After the planning migration, attach executable scope, verification, independent review, and implementation
  completion to TASKs. TICKET and EPIC progress rolls up accepted child outcomes without implying publication or
  merge. Keep feature branches from `develop`; no branch renaming or managed-agent machinery is implied.

### Planning model migration

Adopt the following hierarchy for new work once the migration is verified:

| Record | Responsibility | Completion boundary |
| --- | --- | --- |
| EPIC | Strategic destination, outcomes, scope, and exclusions. | Its accepted requirement outcomes are satisfied; not a release claim. |
| TICKET | A cohesive group of requirements, use cases, and observable acceptance criteria; may span several PRs. | Required TASK outcomes satisfy the accepted requirements. |
| TASK | An independently implementable and reviewable slice, normally one PR, linked to its owning TICKET. | Accepted implementation and required verification; publication and merge remain distinct. |

- Update local conventions, agent/contributor routing, templates, identifiers, parent/dependency validation,
  progress indexes, and execution-board rules together. Define readiness and completion at each level; requirements
  acceptance alone must not make a TICKET executable as though it were a TASK.
- Make TASKs the implementation frontier and retain an explicit human-decision frontier. Define one authoritative
  execution board and update the "What's next?" contract and all callers without competing old/new frontiers.
- Document a bounded bootstrap/cutover path so the migration itself can be authorized and verified under the current
  lifecycle. Identify the transition point for new requirement TICKETs and executable TASKs; do not require absent
  templates or unsupported validator behavior to complete the migration.
- Preserve existing PRDs and legacy executable tickets as addressable records with their original IDs, meanings,
  links, evidence, and status history. Define how validators distinguish legacy records from new requirements;
  never silently relabel a legacy ticket as a TASK, reuse its identity, or renumber it to resemble new work.
- PRDs cease to be a required intermediate layer for new work after cutover. Existing PRDs remain valid historical
  or continuing authorities until an explicitly linked successor takes over; they are not automatically archived.
- Record whether unfinished [T-00004](../tickets/00004-TICKET.md) continues under explicit legacy rules or receives
  a linked successor. Preserve its owning-package evidence gate and `needs-info` boundary; do not mark it complete,
  make it executable, or retire its parent merely to finish the planning migration.
- Verify the new hierarchy and legacy coexistence through actual planning validation, link/dependency inspection,
  and direct routing checks. Do not introduce product tests of planning tooling or deliberately invalid fixtures.

[Local conventions](../CONVENTIONS.md) and [the stable Board](../tickets/BOARD.md) define the guarded migration.
The approved requirement records remain non-executable and retain their IDs. John authorized TASK-00001 execution
in the current checkout on the existing branch under
[T-00008's bootstrap exception](../tickets/00008-TICKET.md#approved-bootstrap-exception). Independent acceptance and
[authorized cutover](../tasks/00001-TASK.md#cutover-and-closeout) now complete that migration. New work follows the
active lifecycle and still needs approved TASK scope and execution authority. No legacy record is moved or reinterpreted.

### Explicit exceptions and retained authority

| Boundary | Retained local authority |
| --- | --- |
| Framework and composition | Symfony-native services, Kernel, compiler passes, and adapters; no framework migration. |
| Coverage | Exact Unit-only coverage remains mandatory, not an aspirational percentage or combined-suite substitute. |
| Infrastructure | [WF-002](../wayfinder/tickets/WF-002-local-development-runtime-contract.md) retains its accepted MySQL/Redis/Mercure and isolation direction; no topology is implemented or replaced here. |
| Public contracts | Owning package releases and audited signatures take precedence over consumer naming or wiring preferences. |

Other exceptions require a demonstrated reason, an affected requirement, local acceptance, and a verification
path. They must not silently weaken coverage, hosted checks, or public API compatibility.

## Scope and sequencing

1. Establish the planning migration and its bootstrap/cutover path, preserving legacy authorities while enabling
   EPIC -> TICKET -> TASK for new work. Reconcile lifecycle guidance and execution routing before relying on it.
2. Codify the accepted ownership, naming, testing, review, and delivery requirements in focused local guidance,
   recording precise supersession of existing instructions and attaching implementation acceptance to TASKs.
3. Align gate orchestration, explicit preparation, hosted setup, and durable Unit coverage reporting without
   weakening the current checks or clean-clone experience.
4. Align existing presentation code and test boundaries in bounded slices with equivalent or stronger evidence.

This sequence describes outcomes, not executable work items. John approved the five requirement areas recorded
below, replacing the earlier four-ticket/supporting-PRD proposal. John also approved one atomic migration TASK
and the bootstrap exception under [T-00008](../tickets/00008-TICKET.md), then authorized execution in the current
checkout on the same branch. Current conventions plus that bounded exception govern the bootstrap;
the verified hierarchy governs new work after cutover. No intermediate PRD is created. Executable slices must
name affected adapters, package assumptions, documentation changes, verification, and exclusions.

The current gate and retained-boundary policy in [PRD-00002](../specs/00002-PRD.md),
[T-00003](../tickets/00003-TICKET.md), and [T-00007](../tickets/00007-TICKET.md) remain the operational baseline
until their replacements are verified. Preserve those completion records as history; later tickets must state
exactly which mechanics or test classifications they supersede, never imply that stronger coverage is retired.

## Dependencies and exclusions

- The [AccessControl starter map](../wayfinder/symfony-access-control-application-map.md) remains separate. This epic
  neither closes it nor substitutes for its implementation handoff. Guidance, gate, and homepage alignment do not
  wait on unreleased application capabilities.
- Before any new AccessControl use case or binding, reconcile the installed scaffold with an explicitly accepted
  released baseline through [WF-001](../wayfinder/tickets/WF-001-released-package-contract-audit.md). Audit immutable
  release identity, schemas, public signatures, and compatibility; do not select a version because another consumer
  installs it. Package resolution changes need their own local authorization and verification.
- Exact API, persistence, authentication, authorization, asynchronous delivery, realtime, and browser contracts
  remain with the map's owning decisions. No new login, database schema, migration, endpoint, worker, provider
  effect, browser journey, or full runtime topology belongs to this epic.
- No dependency update, upstream package modification, global standards rollout, runtime enrollment, release,
  publication, visibility transition, deployment, or archive operation is authorized by this record.

## Completion criteria

- Local conventions, templates, identifiers, validation, parent/dependency rules, and one execution frontier support
  EPIC -> TICKET -> TASK with a verified cutover. A normal new-work request routes from requirements to an approved
  TASK; an unaccepted requirement or unresolved blocker cannot be mistaken for executable work.
- Legacy PRD/ticket references, meanings, and historical evidence remain intact. T-00004 has an explicit continuation
  or successor disposition preserving its unmet package gate, with no automatic renumbering, closure, or archive.
- Local contributor and agent guidance states the adopted requirements and explicit exceptions without conflicting
  instructions or dependence on private reference material.
- Existing owned PHP and homepage presentation satisfy those conventions or have individually accepted exceptions;
  route, rendered behavior, and package boundaries remain intact.
- Every retained or replaced test has a clear owned contract or an equivalent direct diagnostic; meaningful
  framework integration evidence and exact Unit coverage are preserved.
- The canonical running-container gate executes all required phases and retained suites without duplicate test
  execution, preserves the Unit report, and demonstrates failures through the real commands rather than tool tests.
- Fresh clean-clone local and hosted verification proves the documented preparation and gate contract. Record
  actual results, counts, driver/coverage denominator, warnings, and limitations; historical reports are not proof.
- Independent Spec and Standards review accepts each implementation slice with traceable snapshot evidence. After
  cutover, TASK records own that evidence and implementation completion; requirement progress, hosted verification,
  publication, and merge remain distinguishable.
