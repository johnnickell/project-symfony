# WF-001 — AccessControl v0.4.0 released-contract delta

Research date: 2026-09-28. Scope: public immutable release artifacts and consumer contracts only.
Owner: [WF-001 — Released Package Contract Audit](../tickets/WF-001-released-package-contract-audit.md).

## Question

Does released AccessControl v0.4.0, with Common v1.2.0, supply the reusable schemas and complete public contract
needed to move the Symfony starter into HTTP, persistence, security, and worker decisions?

## Short answer

**The release exists and its declared dependencies admit Common v1.2.0. The schema gate is not yet satisfied.**
The published distribution contains 85 reusable schema anchors under `openapi/`, not `resources/openapi/`.
However, its invitation-status schema contradicts its own released safe view, and its catalog omits the new
credential-delivery command, queries, and results. Retain WF-001 **Open** for an owner disposition of those findings;
do not close WF-003, duplicate package schemas in Symfony, or assume forthcoming v0.5.0 fixes them.

The material baseline changes are the opt-in schema catalog, recoverable credential delivery, supported
`TransactionalUnitOfWork` composition, non-null Permission tiers, and consumer-owned entry-point authorization
for Role/User-Role/Agent-Permission administration. No dependency installation, application implementation,
package modification, release action, or consumer certification occurred.

## Schema findings

### F-01 — Invitation status schema disagrees with the released view

The immutable [catalog][catalog] declares `Fight.AccessControl.InvitationDeliveryStatus.status` as:

```text
pending, claimed, failed, confirmed, expired
```

The released [InvitationDeliveryStatusView][invitation-view] accepts `CredentialDeliveryStatus` and exports its
literal `value` through `toArray()`. That [enum][delivery-status] declares:

```text
pending, claimed, retry_pending, delivered, permanent_failure, expired, invalidated
```

Thus `delivered`, `retry_pending`, `permanent_failure`, and `invalidated` are valid released values rejected by the
schema; `failed` and `confirmed` are obsolete values still admitted by it. The typed invitation-status JSend
wrapper references that same component. This is a source-level contradiction, not an inference from a future
release or an optional CI result. It would also affect bindings generated from that component.

**Disposition:** unresolved package-owned schema defect under the retained reusable-schema requirement. Prefer a
corrected immutable package release and a focused re-audit. Any decision to exclude the affected capability or
change schema ownership requires John's explicit amendment; this audit makes neither change and selects no new
version automatically.

### F-02 — New delivery contracts lack catalog entries

The complete catalog has **85 unique** `OA\Schema` anchors. Comparing the released command/query names against
all anchors finds no corresponding entries for:

- `DeliverPasswordReset`;
- `FindCredentialDeliveryStatus` and `FindDueCredentialDeliveries`;
- their new safe result shapes, `CredentialDeliveryStatusView` and `DueCredentialDelivery`.

The new [status view][delivery-view] exports `purpose`, `delivery_id`, `user_id`, `revision`, `status`, `due_at`,
`expires_at`, `attempt_count`, `last_attempt_at`, `last_outcome_at`, and `last_failure`. The [due-work value][due-work]
exports `purpose`, `delivery_id`, `user_id`, `due_at`, `revision`, and `status` without destination or credentials.
Neither is equivalent to the old three-field invitation-status component. [Delivery migration][delivery-guide].

**Disposition:** catalog coverage gap, distinct from F-01's incorrect existing schema. Worker-only messages do not
necessarily need HTTP schemas; their omission alone does not make a worker contract unusable. Record an explicit
coverage/exclusion decision before claiming a complete HTTP catalog, especially for the proposed operational
status read. Do not silently invent matching package schemas in Symfony.

### Verified catalog boundary

The package ships `openapi/bootstrap.php` loading `openapi/Components.php`. It supplies schemas only: no document
root, paths, methods, operation IDs, servers, security schemes, status-code decisions, or UI. The documented
consumer scan combines the package bootstrap/catalog and consumer anchors in one pass. Optional JSend success
components are response-shape choices, not package-owned endpoints or mandatory Symfony envelope semantics.
[Composition guide][openapi-guide], [bootstrap][bootstrap], [catalog][catalog].

Static checks also confirm the Permission component requires a non-null tier, the browser authentication response
omits `refresh_token`, the portable TokenSet includes it, and password/credential request properties are write-only.
These are carrier facts, not accepted cookie/HTTP policy. No generator was installed or executed here; OpenAPI 3.1
composition, reference resolution, normalized drift checking, and consumer-wire mapping still need their own proof.
The concrete F-01 mismatch prevents treating a successful scan alone as contract correctness.

## Material delta and downstream obligations

### Recoverable credential delivery — WF-004 and WF-007

The [v0.3 migration contract][delivery-guide] replaces `InvitationDeliveryInvoker` and `EmailChangeDeliveryInvoker`
with `CredentialDeliveryProvider::deliver(CredentialDeliveryInvocation): CredentialDeliveryOutcome`. Three
purpose-specific cipher interfaces extend `CredentialDeliveryCipher` and require both encryption and
`decrypt(EncryptedCredentialMaterial): string`. Raw ciphertext getters are replaced by a protected boundary value.

- Persist the full delivery generation, claim/lease, due time, attempt/outcome metadata, aggregate revision, and
  safe failure classification. Each grant repository supplies `findDue(DateTimeImmutable $at, int $limit): array`.
- Repositories in a handler must share its physical transaction connection. Complete-state compare-and-set and
  atomic audit persistence are required; a separate commit in one adapter is not equivalent.
- Direct delivery commits a claim, then decrypts/invokes outside the transaction, then commits the typed outcome
  under exact claim/generation/revision authority. Provider outcomes are `DELIVERED`, `RETRYABLE_FAILURE`, and
  `PERMANENT_FAILURE`; safe failure values are `retryable_provider`, `unexpected_provider`, and `permanent_provider`.
- Schedule due discovery even when optional post-commit subscribers provide immediate dispatch. Pending work,
  due retries, and expired leases are rediscoverable. Async scheduling enqueues at most one bounded page per cycle;
  looping a full page before workers claim it can enqueue the same work repeatedly.
- The delivery ID is the stable provider idempotency key across retries. This is at-least-once invocation, not
  exactly-once effect. Queue only secret-free package commands, never the credential-bearing provider invocation.
- Do not add another outbox/state machine for package-owned claim, lease, retry, or material-destruction policy.
  Existing data upgrades require the guide's stable-snapshot, external-effect reconciliation, and rollback policy;
  this starter has not implemented or qualified such persistence.

The new due query requires `at` and a positive `limit`; the exact-generation status query requires a nonempty
`delivery_id` and purpose `activation`, `password_reset`, or `email_change`. These are package query contracts,
not chosen HTTP input rules. [Query definitions][delivery-queries].

### Transactions — WF-004

Transaction-aware public constructors now require Common's supported `TransactionalUnitOfWork`, not deprecated
`UnitOfWork` or standalone `commit()`. The baseline legacy-binding warning does **not** apply to v0.4.0. Supply
`commitTransactional()` and `isClosed()` through the consumer's supported transaction adapter; prove real shared
connection/rollback behavior later. [README transaction composition][readme], [changelog][changelog].

### Permission tiers and caller policy — WF-004, WF-005, WF-006, WF-008

The [v0.4 migration guide][tier-guide] and public [Role][role-repository], [Agent][agent-repository], and
[Permission][permission-repository] repository contracts establish:

- `Permission::getTier()` and `PermissionView::getTier()` are non-null. Custom Permissions are `ADMIN_SAFE`;
  protected `SUPER_ADMIN_ONLY` membership belongs only on the uniquely authoritative managed `ROLE_SUPER_ADMIN`.
  Reject/quarantine missing, invalid, or null legacy tiers instead of defaulting them to safe.
- Custom Role lifecycle/membership, User Role assignment/removal, and direct Agent Permission handlers retire
  `RoleAdministrationAuthorization`, `UserRoleAssignmentAdministrationAuthorization`, and
  `AgentPermissionAdministrationAuthorization`, with their corresponding authorization exceptions. Actor IDs are
  provenance, not credentials. Symfony must protect **every** entry path, including direct bus, CLI, worker, and
  idempotent no-op calls. Package tier checks do not replace caller/target authorization or final-admin safeguards.
- Custom-Role grants and Agent grants/replacements require authoritative `ADMIN_SAFE` definitions even on no-ops.
  `RoleRepository::validateCustomPermissionGrant()` and `AgentRepository::validatePermissionAssignments()` must
  share transaction-duration identity/tier fences with writes and managed promotion; a preflight lookup is insufficient.
- `AgentRepository::hasPermissionAssignment()` supports promotion checks. `PermissionRepository::replace()` must
  atomically reject promotion while custom Role, ordinary managed Role, or Agent membership remains. Promotion
  does not silently strip membership. Wire the Agent repository into `ManagedPolicyPlanner`; omission rejects
  promotion closed. Exact database locking remains Symfony-owned.
- Role IDs and canonical names must be unique and lookups unambiguous. The reserved Super Admin Role cannot be
  custom. Pending Users may receive the managed Role during bootstrap, but only active Users authenticate.
- Retained invitation-correction, session, and email-change ownership-sensitive authorization ports are not removed
  by this change. Do not generalize the three retired ports into "the package does no authorization."

### Results, events, and failures

Ordinary reads still return safe Views/ResultSets; mutations retain command/event semantics. TokenSet and Agent
provisioning/rotation results remain secret-bearing synchronous results, never ordinary read models. Refresh retains
rotated/conflict handling; this delta does not authorize changing the baseline token lifetime or refresh policy.

No baseline Domain Event type was removed or added in the artifact name comparison. The 40 events remain:

## Verification, sampling, and limits

Performed successfully:

1. Remote tag queries for AccessControl v0.4.0 and Common v1.2.0; Packagist metadata fetches and reference comparison.
2. Download of the advertised immutable v0.4.0 distribution and the immutable v0.1.0 baseline; v0.4.0 tree/blob check.
3. Full release manifest, changelog, README, two migration guides, OpenAPI guide, bootstrap, and catalog inspection.
4. Artifact symbol-name inventory plus a public declaration/signature comparison across baseline and target;
   targeted reading of changed repository ports, query/result contracts, provider/cipher ports, and status enum.
   Signature extraction was a textual orientation aid, not a PHP type checker or behavioral equivalence proof.
5. Independent deterministic catalog-name/enum set comparison: 85 unique schemas, four current invitation status
   values missing, two obsolete values present, one Command and two Queries without same-named catalog components.

Scratch downloads and comparison outputs are under ignored `.runs/2026-09-28-wf-001-v040/`. Durable authority is
this note's immutable public citations, not scratch availability. No upstream source is adopted into production.

Not performed: package test reruns, PHP execution of DTOs, swagger generation, Composer solve/install, actual
consumer database/concurrency tests, application boot, HTTP/browser tests, canonical build, or hosted verification.
The Docker services were not running and were not started for this static audit. No signature-trust validation or
complete implementation-body/security audit is claimed. The schema mismatch is directly demonstrated by public
value/serialization contracts despite those limits. These limits prevent consumer certification, not reporting F-01.
